# Binary query writer: technical analysis

This section describes the current production change relative to upstream `main` revision `5434e51194e6c2e1aa745e5d65a4c998918d6073`. It explains mechanisms and tradeoffs; performance results belong to the separately recorded comparisons. The implementation is in [BinaryQueryResultWriter.java](../core/queryresultio/binary/src/main/java/org/eclipse/rdf4j/query/resultio/binary/BinaryQueryResultWriter.java).

## Encode core datatype names once, then patch document-local fields

The core datatype vocabulary is a good target for pre-encoding: the same immutable datatype IRIs occur on many literal records. The writer now builds a static table of QName templates for the `CoreDatatype.XSD`, `CoreDatatype.RDF`, and `CoreDatatype.GEO` enums. Their local names are encoded to UTF-8 once during class initialization, shared across writers. This is once per defining class loader, normally once in the application JVM. The arrays are private, never exposed, and never modified after initialization.

Each template already contains the complete QName representation except the namespace ID:

| Field | Size | Ownership |
| --- | ---: | --- |
| QName record marker | 1 byte | Shared constant |
| Namespace ID | 4 bytes, big-endian | Patched for the current document |
| Local-name UTF-8 byte length | 4 bytes, big-endian | Precomputed constant |
| Local-name UTF-8 payload | Variable | Pre-encoded constant |

On the first use of a canonical datatype in a document, the writer looks up or declares its namespace, clones the matching template, and patches bytes 1–4 with that document's namespace ID. Subsequent literals write the cached record directly. Their datatype path no longer extracts the local name, encodes it, performs another namespace lookup, or separately writes the QName's marker, ID, length, and payload. `startQueryResult()` clears the writer's cached records together with its namespace table. The static templates remain reusable.

Namespace IDs cannot be embedded once globally: they depend on the namespaces encountered earlier in each result. The namespace declaration must also precede the typed-literal marker; the parser expects the datatype QName immediately after the literal label. The cache preserves that ordering. Enum ordinals index only the internal cache and are never serialized. These constraints follow from the [baseline writer](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/queryresultio/binary/src/main/java/org/eclipse/rdf4j/query/resultio/binary/BinaryQueryResultWriter.java) and [parser](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/queryresultio/binary/src/main/java/org/eclipse/rdf4j/query/resultio/binary/BinaryQueryResultParser.java).

The fast path requires `datatype == coreDatatype.getIri()`. Equal IRI text alone is insufficient to preserve the old bytes: an alternate IRI implementation can expose a different namespace/local-name split. The identity check limits shared templates to the known canonical immutable IRIs. Custom datatypes and noncanonical IRI instances retain the generic path, which preserves their split and reuses its resolved namespace ID rather than looking it up twice. Language and directed-language literals retain their separate language-record representation. The canonical vocabulary is defined in [CoreDatatype](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/model-api/src/main/java/org/eclipse/rdf4j/model/base/CoreDatatype.java).

The tradeoff is bounded storage and startup work: one shared template per core datatype, one reference array per writer, and one small cloned record per datatype actually used in a document. It avoids a growing cache of arbitrary literal strings or IRIs. Equal but noncanonical datatype objects deliberately receive fewer optimizations in exchange for preserving their serialization behavior.

## Binary framing still requires UTF-8

The binary query result format specifies ordinary UTF-8 strings preceded by a four-byte big-endian **byte length**. Binary record markers remove textual framing; they do not specify a charset-free representation of Unicode. Raw Java UTF-16 characters, Latin-1 bytes, `DataOutputStream.writeUTF()`'s modified UTF-8, or LMDB value IDs would change the protocol. NUL uses one zero byte; a supplementary character uses four UTF-8 bytes. See the [pinned format constants](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/queryresultio/binary/src/main/java/org/eclipse/rdf4j/query/resultio/binary/BinaryQueryResultConstants.java) and the parser above.

The implementation removes repeated encoding where bytes are constant, and reduces allocation and framing overhead for changing strings. Each writer retains a 4,100-byte scratch array: four bytes for length and 4,096 bytes for payload. ASCII strings up to 4,096 characters copy directly into it. Other strings of at most 1,365 UTF-16 code units use a strict UTF-8 loop; the three-bytes-per-code-unit bound guarantees capacity, including valid surrogate pairs. The code fills the length prefix after encoding and sends prefix plus payload in one bulk write. No bytes of the current string are emitted before encoding succeeds.

Larger strings retain the existing `CharsetEncoder` fallback. This bounds retained scratch memory instead of retaining an array as large as the largest observed literal. It also means large strings still incur the old output-buffer allocation; some non-ASCII strings that could fit are conservatively routed to that fallback. A separate large-string optimization would need to justify a byte-length pass, streaming complexity, or additional retained memory.

Malformed surrogate input still raises `MalformedInputException`. Replacing the runtime path with `String.getBytes(UTF_8)` would silently change that behavior to replacement. The static templates can use `getBytes` safely because their inputs are the known valid vocabulary constants. The distinction follows from the [Java 25 String contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/String.html) and [CharsetEncoder contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/charset/CharsetEncoder.html).

## Reduce equality and stream-call overhead without changing LMDB

The writer keeps a `Value[]` for the previously observed columns. This removes the previous row's binding-name lookup and avoids retaining a possibly reused `BindingSet`; lookup of the current row's value still occurs. It checks object identity before invoking `equals`, so repeated identical objects bypass `LmdbLiteral.equals`. Distinct objects still use their normal equality semantics. Comparing numeric LMDB IDs in the generic writer would be unsafe without the associated revision, canonicality, and mutation rules; those remain the model's responsibility. See [LmdbValue.equalsNative](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/model/LmdbValue.java#L109).

Adjacent NULL and REPEAT markers are collected in a column-width array and drained before a value or at the end of the row. A singleton still uses a scalar write. An EMPTY_ROW preserves the previous tuple, matching the parser's repeat semantics. The cached datatype record and framed short strings similarly combine existing wire bytes into fewer output calls.

This matters because the actual [QueryResponseHeartbeat payload wrapper](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/http/client/src/main/java/org/eclipse/rdf4j/http/client/QueryResponseHeartbeat.java) synchronizes and checks state on writes even though binary results do not schedule whitespace heartbeats. The change does not add a persistent `BufferedOutputStream`: successful callback output is drained, while explicit and final flush behavior stays in the existing stream chain. Write granularity and partial-row failure timing can still change; the design avoids retaining completed-row bytes across callbacks. Details are in [the lifecycle analysis](buffering-lifecycle.md).

## Relevant primary implementation comparisons

| Implementation | Applicable technique | Constraint for this writer |
| --- | --- | --- |
| [OpenJDK 25 String](https://github.com/openjdk/jdk25u/blob/master/src/java.base/share/classes/java/lang/String.java) and [UTF-8 encoder](https://github.com/openjdk/jdk25u/blob/master/src/java.base/share/classes/sun/nio/cs/UTF_8.java) | Specialized string encoding can bypass generic character-buffer operations. | `String.getBytes` still allocates and has different malformed-input semantics. Reusing a `CharsetEncoder` does not make its convenience `encode(CharBuffer)` output allocation-free. |
| [Apache Avro BinaryEncoder](https://github.com/apache/avro/blob/main/lang/java/avro/src/main/java/org/apache/avro/io/BinaryEncoder.java) and [Utf8](https://github.com/apache/avro/blob/main/lang/java/avro/src/main/java/org/apache/avro/util/Utf8.java) | A bounded reusable ASCII buffer; an existing UTF-8 value can be written directly without decoding and re-encoding. | Avro's `getBytes` fallback is not RDF4J's strict error contract. A byte-oriented value requires correct ownership and lifetime. |
| [Protocol Buffers CodedOutputStream](https://github.com/protocolbuffers/protobuf/blob/main/java/core/src/main/java/com/google/protobuf/CodedOutputStream.java) | Reserve prefix space, encode into owned output storage, then fill the length. | RDF4J's fixed four-byte length is simpler than a variable-length prefix, but an arbitrary stream cannot backpatch bytes already emitted. The scratch array supplies the necessary owned storage. |

The inspected external snapshots and source blob identifiers are recorded in [the protocol research](protocol-research.md); the RDF4J links here are pinned to the baseline revision. These are design comparisons, not claims that the formats or error contracts are interchangeable.

## LMDB UTF-8 forwarding is a separate representation change

Many LMDB dictionary records already contain UTF-8 lexical bytes. Literal records contain UTF-8 labels and language data after datatype/header fields; IRI records contain a namespace ID and UTF-8 local name. Namespace bytes reside in another record. Forwarding those bytes could avoid a decode/re-encode cycle, but store namespace IDs still need translation to result-document IDs. [ValueStoreRecordCodec](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/ValueStoreRecordCodec.java#L81) describes those layouts.

There is no universal byte slice for every value. Short inline strings pack up to six UTF-8 bytes into an ID. Inline numeric, boolean, and date/time representations need their matching lexical conversion. Triple terms require recursive component resolution. The memory-only compressed overlay may need selective decoding, and callback-scoped record access cannot escape its source lifetime. An owned record view is safer to retain but already entails a copy. Avoiding charset conversion is therefore more precise than promising zero-copy IO. See [inline strings](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/inlined/Strings.java#L24), [owned/scoped record access](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/ValueStore.java#L5915), and [the visitor lifetime contract](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/valueoverlay/ValueStoreRecordVisitor.java#L21).

The current [repository result boundary](https://github.com/eclipse-rdf4j/rdf4j/blob/5434e51194e6c2e1aa745e5d65a4c998918d6073/core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/RepositoryValueIteration.java#L145) resolves unprepared values before returning them. Fetching their bytes again in the writer would keep the original decoding work and add a lookup. A useful extension would preserve owned UTF-8 payloads during materialization, expose an optional store-independent capability, and materialize Strings lazily, or provide a separate native sink inside the correct resolution scope. Either needs captured revision/epoch ownership, mutation invalidation, language/direction handling, externally visible blank-node identities, and fallback for computed values. That scope is distinct from the generic writer optimizations described here.
