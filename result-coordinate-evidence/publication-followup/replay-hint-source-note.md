# Replay eligibility across native IR: a source-level lead

This is a static source note written during the timing quiet interval. It does not read timing samples, run new experiments, change code or select a next implementation. The completed publication diagnostics make replay eligibility worth examining, but the fixed timing results must determine whether pursuing it is useful.

The main finding is more specific than “a negative replay hint was dropped.” The direct factorized cursor can exclude some targets, and the final buffered IR adapter conservatively treats every valid captured coordinate as eligible. However, the interpreted-plan bridge between them already checks the producer's negative eligibility before it captures a coordinate. There is no evidence here that simply copying an existing boolean through that bridge would remove the fixture's unused pages. Native IR can also construct coordinates directly from domains and adjacency probes, under a separate conservative structural analysis.

## What the contract means

`NativeResultCoordinates` is declared near the top of `core/sail/lmdb/src/main/java/org/eclipse/rdf4j/sail/lmdb/evaluation/LmdbNativeFactorizedRows.java`. Its `mayReplay(int slot)` contract says that false excludes a slot for the current binding, while true may conservatively include slots that do not replay. The default is true. The contract is an eligibility interface; it does not promise that every false value is a structural proof that an origin can never recur. For example, the factorized cursor's implementation also returns false when its coordinate mapping was refused.

`LmdbNativeFactorizedRows.Cursor.next()` resets `replayableSlots` for a new prefix and computes an `earlierCanVary` flag while examining enumeration branches. A branch's value slots become replayable when an earlier enumeration branch can vary; `earlierCanVary` becomes true when a previous branch's actual result count exceeds one. The cursor's activation is tied to `coordinatePrefix`, and ordinary fallback or an inactive enumeration disables its coordinate view. Its `resultCoordinate()` itself checks `mayReplay()` before returning group, parent, position and tuple-column fields.

This is a useful local, runtime-sensitive distinction between a first enumeration branch and later branches. It is not automatically a certificate about the complete lifetime of a surrounding buffered or nested execution.

## The exact bridge and buffered adapter

`LmdbNativeKernelExecution.FusedRuntimeRowCursor` explicitly delegates `mayReplay()` to its coordinate-aware child. That wrapper does not replace the hint with unconditional true.

`LmdbNativeKernelBindings.BoundPlan.openCoordinates()` maps requested outputs to source slots and installs coordinate demand on the forked row. `BoundCursor.fillRows()` advances that source, captures output values and invokes `captureCoordinates()` before advancing again. The capture method first invalidates the destination cell by setting position to -1 and namespace to zero. It then refuses capture when the producer activation is invalid, `source.mayReplay(slot)` is false, or the slot fails `coordinateValid()`. Only a successfully recaptured origin receives a mapped positive namespace and is copied into the primitive sidecar. Changes in source activation retire the previous mappings, while reference accounting protects buffered coordinates that remain exposed.

The interpreter's `PlanRows` pull stage calls this bridge through `fillCoordinates()`, imports each captured tuple with `KernelResultCoordinates.set()`, and releases the sidecar batch afterward. Generated PlanRows code in `LmdbNativeKernelEmitter` also uses `fillCoordinates()`, with a larger bounded batch when allowed. Thus the source's false eligibility is already honored on this path in both tiers: the output cell remains unavailable rather than becoming a valid coordinate with a separate false flag.

`KernelResultCoordinates` stores five-word origins, manages namespaces and saved frames, and snapshots origins at terminal emission. `set`, `copy`, `save`, `restore`, `emit` and the buffered output representations preserve coordinate identity and its lifetime. There is no independent replay-eligibility bit in those tuples. `hasCoordinate()` checks active-row availability, nonnegative position and a positive namespace.

The final adapter is `LmdbNativeKernelExecution.KernelRowCursor`. It fills a value buffer through `LmdbNativeJaninoCodegen.fill`, maps physical output columns to engine slots while binding each buffered row, applies residual filters, and exposes the accepted `coordinateRow`. Its activation is 1 for a valid live buffered row. `coordinateValid()` checks that the slot maps to an output column with a valid buffered coordinate. Its `mayReplay(slot)` returns exactly `coordinateValid(slot, 1L)`. It therefore expresses conservative eligibility for every valid captured coordinate. This behavior by itself does not show that an earlier false hint was lost: on the direct PlanRows bridge described above, false prevented a valid tuple from being captured in the first place.

## A separate source of conservative eligibility

`LmdbNativeKernelExecution.resultCoordinateColumns()` chooses tracked outward registers using `coordinateReplaySourceColumns()` and alias propagation. The structural helper carries a boolean `precedingExpansion`, descends through left groups, lexical-frame joins and unions, and conservatively includes PlanRows outputs because one bridge can contain an independent factor product. `coordinateExpansionDepth()` is capped at two and does not use the actual per-binding result counts employed by the direct factorized cursor.

Native IR producers do not all obtain coordinates from `NativeResultCoordinates`. For example, the interpreter directly calls `KernelResultCoordinates.set()` when enumerating a domain or reading a bound adjacency run. A domain origin uses its domain group and member position. A probe origin uses its adjacency group, source-run token, member position, tuple column and namespace. Generated code has corresponding direct `rc.set(...)` paths. Those origins reach `KernelRowCursor` under the coarse tracked-column analysis, without an underlying `mayReplay(false)` value waiting to be forwarded.

This suggests a source-level question: does the structural analysis include a producer merely because an earlier site can expand, even when earlier variation changes the producer's parent key so that its complete origin cannot return? A one-row earlier site or a monotonically changing parent can make “earlier expansion exists” more conservative than actual reuse requires. This is a hypothesis about possible over-inclusion, not an attribution of the current fixtures. The publication diagnostics identify requested targets and complete page keys; they do not record the lowering node or producer kind responsible for each target. That mapping should be established before blaming an adapter or choosing a representation change.

## Proof and experiment obligations before a general rule

A negative eligibility value must be scoped to the binding and coordinate lifetime in which it is valid. The factorized cursor changes activation with its prefix; the final buffered cursor has one broad activation while exposing rows from multiple source generations. Reading a producer's current hint after it has advanced cannot describe an older buffered row. Any new metadata must follow the relevant register, alias, frame, emitted row and namespace, or be replaced conservatively when the execution context changes.

Local non-replay does not establish global non-replay. A surrounding join, union arm, restored frame, nested producer or later parent revisit can expose the same origin after the ordinary memo has changed. A claim that no useful reuse is lost must reason about the canonical target/cache bank and the full namespace, group, parent, position and tuple-column key, as well as winning source occurrences, unbound gaps and accepted/rejected rows. Monotone position within one run is insufficient if the parent or frame can return.

The current omission experiment removes publication only. `NativeResultMaterializer.captureCoordinate()` consults `mayReplay()` for both factor lookup and publication. Replacing the fixture mask with a false result at that interface would also suppress lookups; pruning tracked columns earlier could additionally remove coordinate transport and change memory claims. Those would be different interventions and should be qualified separately. The cost of carrying, updating and accounting for an extra hint must also be measured; a source-level opportunity is not a free optimization.

Result correctness and preservation of helpful reuse are different requirements. Ordinary resolver fallback can keep results correct when optional publication is omitted, even if a heuristic accidentally rejects a useful future replay. A stronger no-loss claim needs tests or structural reasoning that preserve successful hits after ordinary-cache displacement. The existing `acceptedReplayHitAdmitsItsOriginalFactorCoordinate` contract remains relevant: an ordinary hit at a new accepted coordinate can establish a useful future entry. Blanket omission of ordinary-hit publication would not follow from this note.

If the timing evidence warrants another investigation, the first narrow question is which producer sites and dependency relationships supply the selected unused targets, and whether an existing negative eligibility decision is actually available at the final materializer boundary. A diagnostic can distinguish direct IR origins, PlanRows-imported origins and frame-restored origins before changing policy. Any later implementation would need parity across interpreted and compiled IR, appropriate treatment of all supported transport representations, explicit reservation/cleanup accounting, and cases with nested replay, aliases, early close and retained rows. No such experiment or implementation was performed here.
