# Methods and interpretation boundaries

## The question this experiment answers

The completed compact-page experiment showed that reducing factor-page charge did not by itself recover the latency gap of coordinate-enabled execution. Its diagnostics identified a different opportunity: some targets repeatedly publish factor entries that supply no successful hits in these full-consumption executions. The next useful experiment is therefore to omit that publication while preserving ordinary reuse, useful factor hits, ownership and the native execution route.

The primary estimand is the ratio of total query latency for selected-target omission to all-target publication, within the same fixture and round. Both use identical experimental classes and the original dense factor pages. The intervention removes selected calls' coordinate capture, page lookup/admission, cell comparison/write and subsequent cleanup work. It can also change cache layout and the cost of the surviving lookups. Consequently the measured difference belongs to the complete intervention; it is not a direct measurement of one instruction or a profiler estimate of the original method's self time.

A third arm turns coordinate transport OFF with ordinary reuse enabled. It provides a contemporaneous reference for whether the publication change closes the remaining transport tradeoff under this common runtime. All three arms include the experiment's plan metadata and mask check. The guard executes at different frequencies in OFF and DENSE, so the OFF comparison includes that interaction under the experimental runtime; shared code does not imply equal executed overhead. Absolute timings do not quantify the overhead of the check against an unmodified production class.

## Implementation and source control

The selected production source was not edited. Its materializer SHA-256 remains `cb0749719313b85c8cd134b6c03085f712915188f0e53333cbd46e19e2f0f96e`. All 2,055 LMDB module source/resource files remained identical at preflight. The branch remains `GH-0000-lmdb-lazy-result-coordinates` at `15fe7d5011d27d31d76436238363ee3f34b3ba50`, retaining all earlier uncommitted ownership work.

The complete experimental materializer copy has SHA-256 `25a321a3f9cb590492dc9d4efe0a2022ae4f731b6d90db38c5137a4ee1c21fb1`. It adds one immutable per-plan boolean array and parses the comma-separated experiment property during plan construction. An entirely empty property means no omission. Unknown names, duplicate entries, empty elements inside a nonempty list and noncanonical alias names fail during setup. The hot-path change is a guard at the beginning of `rememberFactor` that looks up `plan.omittedFactorTargets[plan.aliases[target]]` and returns for excluded targets. The remainder of the materializer body is byte-for-byte identical at source level after removing that guard. Ordinary reuse, factor lookup, weak witnesses, ownership, retirement, close and coordinate transport were not rewritten.

The boolean array and plan reference are common experimental metadata outside the existing query ledger. They are included in process allocation measurements. Parsing a nonempty property also adds small setup work to the omission arm, which remains part of the measured intervention. No experimental configuration is installed as a public product feature.

Compilation preserved every emitted class but exposed only the materializer and its plan in a two-class prefix. The original `FactorPage` and `FactorMemo` bytes remain in use. That prefix precedes the exact preserved common 128-entry classpath, producing one 129-entry runtime shared by all arms. Its descriptor SHA-256 is `c46fe65a3515872535b55d0c979bf5f84e4d90b59168c86dd3bc14febaa244b2`. The common harness, oracles, fixtures, original production tree and dependency artifacts were rehashed before the run. Earlier available frozen runtimes, frame and compact-page artifacts were retained; their timings are not pooled into this new study. The fanout harness explicitly identifies its fixture as a reconstruction and historical Stage-2 artifacts as unavailable. This study therefore establishes a matched comparison within the preserved current harness, not a direct rerun of the user's historical Stage-2 measurements. Here, original means the selected dense-page implementation at phase entry, not a historical pre-migration binary.

## Correctness qualification before timing

The required offline root quick clean install succeeded. A fresh isolated baseline ran 106 cases in eight reports with no failures, errors or skips. This selection includes materialization, value reuse, interpreted and compiled coordinate transport, optional fanout, delayed packed rows, frame lifetime, coordinate representations and row selections.

Six new isolated contracts were compiled against the original API and run before the experimental source was generated or compiled. Five failed assertions and one passed, with zero errors. The failures established that the original implementation neither rejects omission configuration nor omits the requested entries. The passing contract protects ordinary-hit publication for enabled targets. After applying the experimental copy, the same existing 106 cases and all six new cases passed. The new cases also cover canonical aliases, aliases beyond target 63, plan configuration stability, normal resolver fallback after an unbound gap or changed source view, retained detached rows, ledger-first closure and repeated close. These are direct materializer contracts with controlled sources and coordinates, not an additional full SPARQL strategy/alias integration matrix.

The initial isolated baseline attempt had 27 setup errors because the copied POM's direct Surefire invocation had not created its fork temporary directory. The missing directory prevented JUnit and Mockito temporary-file setup. All eight initial XML reports and the runner version are preserved. Creating the directory fixed the harness, after which the same 106-case selection passed. No production defect was inferred from that setup failure and no assertion was weakened.

Successful test XML, case identities, physical tested class trees and source maps were independently reconciled before freezing the runtime. All 2,778 production class files matched the intended composition. The fresh build's generated `maven-config.properties` resource differed from the older frozen runtime; both hashes and the exception are recorded. Timing uses the older exact resource consistently in every arm. The selected module's read-only Spotless check also passed.

## Fixtures and the memory control

The fanout fixture uses 100 measurements, 10 readings, 12 projected targets, two statuses and no unique payload expansion. It emits 1,152,000 rows and the established lexical checksum `3123987218479850048`. Its independent expected count and checksum checks remain unchanged.

The shared-tail fixture uses 64 roots, 128 left members, 128 right members and two columns in each tail, giving six projected targets and 1,048,576 rows. Its checksum is `8327963502356915200`. The independent exact bag oracle additionally checks IRI types, lexical values, tuple/parent association, legal unique row keys, multiplicity and the complete count.

The original shared-tail cache exhausted a 256 MiB query allowance. Removing left-target pages could therefore improve useful admissions as well as avoid publication. To separate those effects, every timed arm uses a 512 MiB per-query allowance, while the global query ledger and fixed heap remain 1 GiB. Same-overlay diagnostics established zero factor-page admission refusals and equal resolver/hit counts at that allowance. Separate 256 MiB diagnostics quantify admission relief and are never used as latency estimates.

Target selection was fixed before timing. Shared-tail omits the previously motivated `l0,l1`. The fanout discovery rule requires positive admitted pages and completed publications, with zero factor hits and zero factor weak/witness misses in every one of four diagnostic queries, aggregated by canonical target. It selects exactly `measurement,reading`. Targets with no admitted pages are excluded from the mask. Both fixtures happen to have identity alias mappings; the implementation and contracts still handle aliases explicitly.

## Fixed performance protocol

The design below was fixed prospectively. Execution stopped after nine of the planned 36 JVMs because one warmup resolver count differed. It is an incomplete study with no accepted paired performance estimates; the remaining planned JVMs were not launched.

`protocol.json` was frozen before any timed JVM, SHA-256 `2a94e81f10d63ec177cb998d3270fb9cb48adee569ca1808370f6fc81465107b`. The arms are `off`, `dense-all` and `dense-omit`. Every one of their six permutations is used once for each fixture, and the fixture that runs first alternates across rounds. Each fresh JVM executes eight warmups and five measured queries. The complete design is 36 JVMs, 468 queries, 288 warmups and 180 measured queries.

Java is Eclipse Adoptium 25.0.5+8. JVM flags retain `-Xms1024m -Xmx1024m -XX:+UseG1GC` and the existing hot counters. Native evaluation and direct adjacency remain enabled in PREFER mode, with the same indexes and fixture-specific store configuration. The query strategy is normal AUTO. No native route or IR tier is forced. Every measured query must run compiled native IR; the first query may take the normal interpreted tier.

The driver launches only one Java process at a time and records start/end intervals. Collaborators are restricted to lightweight additive document or script preparation during timing; no builds, tests, profiles, full runtime hashing or compression are scheduled. Only the small experimental prefix and frozen control files are checked between JVMs. Full runtime identity is checked before and after the fixed run. This is coordination of our work and recorded child processes, not a claim of machine-wide exclusive hardware access.

Every query must pass its existing result oracle, complete consumption, normal-AUTO/native route checks, active current-revision adjacency checks and zero ledger endpoints. DENSE arms are paired at every corresponding query iteration, including warmups, and must have exactly equal resolver calls, route/tier histograms and adjacency hit counts. The driver preserves all raw outputs and stops on a process, identity, result or qualification failure. The protocol permits no replacement forks, discarded slow samples, extra rounds after seeing results, or route-forcing rescue.

## Measurements and analysis

The preserved harness records total query latency, all-thread and caller-thread allocated bytes, preparation, evaluation, first-row delay, consumption, close and query-ledger peak. Adjacency observations remain outside the allocation/timing windows. The reported `prepareNs` covers `connection.prepareTupleQuery`. Evaluation and first-row phases include any planning or compilation performed there; the counters do not isolate every optimizer or native compilation cost. Preparation is reported separately from the other phases. The first cold query begins after fixture/store setup; it excludes JVM launch and fixture construction. Its cost is descriptive and does not substitute for warmed results.

Each fresh JVM contributes the median of all five measured samples. The primary comparison divides omission's JVM median by all-target publication's JVM median in the same round and fixture. The reported estimate is the median of the six paired ratios, together with all six values and their full range. The ordinary-reuse reference comparisons use the same procedure. A table of medians of six JVM medians is useful for absolute scale, but dividing those descriptive values does not generally reproduce the paired-ratio estimate. Fixtures and earlier studies are never pooled.

The prospective mechanism screen requires an omission/all latency median ratio at most 0.95 on each fixture, with every one of the six paired ratios below 1.0. The median all-thread allocation ratio must be at most 1.0, and no paired allocation ratio may exceed 1.02. Exact semantic and route qualifications are prerequisites. The five-percent threshold represents a useful engineering effect; these gates are not significance tests or confidence intervals. Passing would support pursuing a general policy, not promoting a name mask trained on these fixtures.

Raw results are independently recomputed with a separate standard-library analyzer that does not import the timing runner or accept its derived summary as evidence. All warmups and measured samples remain available. The analysis reports full ranges and any anomalous sample patterns rather than choosing a favorable subset.

## Scope of any conclusion

The experiment measures two fixed, repeated, full-consumption workloads on this JVM and host. It does not establish a production classifier, a general proof that a target never returns after ordinary-cache displacement, or behavior under early close, retained rows, varying uniqueness, projection width, repetition or competing query pressure. The new contracts check some lifetime and alias edges, but do not turn those into performance measurements.

Skipping optional publication can preserve result correctness because ordinary resolution supplies a miss. A stronger claim that no useful reuse is ever lost requires structural reasoning over the complete canonical coordinate key, parent/frame recurrence, namespaces, aliases, unbound gaps and accepted/rejected rows. The existing ordinary-hit replay test demonstrates why deleting every ordinary-hit publication would be a different and unjustified performance assumption. The ledger records declared charges, not physical heap residency; allocation records total bytes allocated in the harness window, not retained memory.

No selected production implementation changes solely on the outcome of this fixture-specific experiment. The complete experimental source and patch remain reviewable and reproducible, with all earlier ownership repairs preserved.
