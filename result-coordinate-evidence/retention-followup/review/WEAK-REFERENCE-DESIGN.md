# Weak-reference design and accounting review

This read-only source and documentation review was conducted on 2026-11-17 for the retention experiment. It does not claim a successful implementation or measured object sizes. No JVM was launched during the review. The current study's implementation, tests and frozen runtime determine whether these recommendations were adopted.

## Preserve the identity contract without preserving the graph

The existing strong direct memo holds both `Value[]` and `InternalIdentity[]`. `InternalIdentity` contains a `ValueStoreRevision`. In the checked-out source, lazy revisions hold the underlying revision, a ValueStore, an association, a retained epoch and a resolution scope; snapshot revisions can hold a read snapshot and tracked-value state. Weakening only the value array therefore leaves a strong ownership path.

For the weak arm, an `Object[]` slot may strongly hold a `WeakValueEntry extends WeakReference<Value>` containing a primitive revision ID and a nullable `WeakReference<ValueStore>` owner witness. Leave the separate identity array empty in that arm. The existing primitive arrays retain the full key and semantic version. A null owner-witness field means that the captured owner was null. A non-null witness which has been cleared is a different state.

Obtain the candidate with one `get()` and keep that same Value in a strong local through all validation. For a captured non-null owner, require a non-null current owner and `expectedOwner.refersTo(currentOwner)`. Java 25 documents that `get()` strengthens the referent and recommends `refersTo` for identity checks that do not need to strengthen it. Passing null to `refersTo` also tests whether a reference has been cleared. `reachabilityFence` preserves deliberately retained diagnostic roots against early liveness optimization. See the [Java 25 Reference API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ref/Reference.html).

Do not use a weak reference to an Entry bundle: the bundle could disappear while a user row still owns the Value. Do not replace exact store identity with `identityHashCode`, which is only an integer hash. Equivalent identity-object replacement must remain a hit if ID, semantic version, revision ID and owner identity still match.

## Reference-wrapper reuse and cleanup

A latest-owner weak reference may be reused across slots when it refers to the newly captured owner. This reduces owner-wrapper allocation without retaining the owner strongly. The Value weak-reference wrapper itself must be newly allocated when its referent changes. Keep the memo's key, hash, adaptation rules, source fences and exposure handoff unchanged.

Caffeine v3.2.4 provides a useful implementation comparison. Its `WeakValueReference` is a strongly held wrapper extending `WeakReference`; its reference-queue cleanup removes an entry only when the queued wrapper is still the node's current wrapper. This avoids stale cleanup removing a replacement. For this bounded direct-map table, queue-free cleanup on lookup and rehash avoids that machinery. A cleared referent should count separately from a semantic invalidation or a different-key collision. Occupied wrapper slots and live referents are distinct statistics.

Both were read through the GitHub file tool. No Caffeine code was copied and no dependency was added.

## Metadata bound and replacement overlap

The local Temurin 25.0.5+8 source archive confirms four instance reference fields in `Reference`: referent, queue, next and discovered. `WeakReference` adds no instance fields. With a 16-byte object header, 8-byte references and ordinary object alignment no larger than 16 bytes, a WeakValueEntry adding one long and one owner reference fits in 64 bytes; an owner WeakReference fits in 48 bytes. Thus 112 bytes per slot is a conservative shallow metadata estimate for that layout. This must be checked against the selected JVM configuration rather than treated as a Java specification guarantee.

For N slots, the simplest unconditional metadata reservation is `112*N + 160`: N complete slot pairs, an additional latest-owner witness of at most 48 bytes, and a replacement pair of at most 112 bytes while the old slot remains live. A smaller `112*N + 112` can be justified if every orphan latest-owner witness is always offset by an empty or ownerless slot and publication preserves that invariant. Saving 48 bytes is not worth making the accounting depend on that invariant. Reserve before allocating. Keeping both old and new capacity reservations during resizing is conservative even when rehash shares existing wrappers.

The existing five-array estimate `80 + 36*N` combines 16-byte array headers with 8-byte reference elements. This is conservative for the intended compressed-class-header runtime. It is not a fully portable uncompressed-layout formula: disabling compressed class pointers can increase array headers to 24 bytes, and 16-byte alignment can round their overhead to 32 bytes for these capacities. Object alignment of 32 bytes also increases the owner wrapper estimate. Pin or record the relevant VM flags and measure the selected layout in a separate diagnostic. If supporting fully uncompressed headers at alignment8, the five-array constant becomes 120; at alignment16 it becomes 160.

The metadata reservation excludes unreachable replaced wrappers awaiting garbage collection, VM reference-processing structures, the memo owner, the ledger reservation object and unrelated query/source objects. Weak Value and owner referents are not strongly retained by these weak slots, but they can remain live through consumers or source caches. A reservation for the selected table's arrays and weak metadata must not be described as a bound on all query or process heap.

## Diagnostics and timing interpretation

Use a source which does not retain returned values for the controlled reachability diagnostic. Separately retain a row, drop rows, replace equivalent identities, and mutate each identity component. Keep the memo alive explicitly. In the real source, `ValueStore.cacheValue` holds canonical and completed values independently of the memo. Its current decoded lexical threshold is 1,048,576 characters; above the threshold it rejects the completed payload and removes a matching canonical entry. Ordinary-sized values therefore cannot by themselves attribute retained heap to this memo.

Use bounded forced-GC diagnostics with a collection canary and no sleeps, and report failure to establish collection honestly. Java's [System.gc contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#gc()) does not guarantee collection or reference clearing for any particular object. The [WeakReference contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ref/WeakReference.html) describes atomic weak-reference clearing when the collector determines weak reachability; enqueueing can happen later.

A small diagnostic instrumentation agent can check shallow object sizes without adding a third-party dependency. [Instrumentation.getObjectSize](https://docs.oracle.com/en/java/javase/25/docs/api/java.instrument/java/lang/instrument/Instrumentation.html#getObjectSize(java.lang.Object)) returns an implementation-specific approximation, not a portable deep-size result. Keep the agent and forced collections out of latency forks.

For performance, hold source-cache settings fixed and use natural GC. Record allocation, GC count/time, collected misses, source calls and checksums alongside latency. Collection-caused loss of reuse is part of the weak-retention result. Caffeine's [reference-eviction documentation](https://github.com/ben-manes/caffeine/wiki/Eviction) also explains that weak values become collectible when other strong references disappear. This experiment should decide whether reduced memo-exclusive retention preserves enough end-to-end benefit; clearing a few weak references alone cannot establish that.
