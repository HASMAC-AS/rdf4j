# Fixed-capacity growth contracts

Prepared before the growth implementation changes, against the admission experiment published at `b8d2015ec1b722b71f9a8af9e50cd98558f7882a`.

The complete source is `test-src/org/eclipse/rdf4j/sail/lmdb/evaluation/NativeDirectValueMemoGrowthContractTest.java`. Its initial sealed SHA-256 is `08187d4f8cf317ca4a66291daf7023bfbdbdf15d4bb7f0afc37961784508ecb2` (18,506 bytes, 12 test methods). The file has the exact 2026 repository header, Codex signature, LF endings and no lines longer than 120 characters. A coordinator may format it before the first execution and record the final source hash; the test source must then remain unchanged across red and green executions.

The smallest pre-implementation selection is `NativeDirectValueMemoGrowthContractTest#fixedGrowthKeeps4096SlotsAtTheFirstGrowthBoundary`. It supplies 16,384 requests with enough hits and collisions to require growth in the unchanged policy. The expected missing behavior is a 4,096-slot table under `rdf4j.lmdb.nativeValueMemo.growth=fixed`; the unchanged runtime is expected to produce 8,192 slots. This is a prospective expectation, not executed test evidence. No Java or Maven process was launched by the contract author.

The full class exercises default and explicit `adaptive` behavior, constructor capture, invalid selection, preservation of the `initial` admission cutoff, permanent initial reservation refusal, and the distinction between skipping growth and having a growth reservation refused. The latter fills the ledger after the first table has been admitted: fixed mode must continue reusing that table, while adaptive mode must keep its existing permanent-fallback behavior. The unknown-selection contract follows the existing exception convention: `IllegalArgumentException("Unknown native Value memo growth")`.

Two paired controls test the intended benefit and the capacity tradeoff. The late cold-hot sequence first supplies 32,768 unique IDs, then makes 98,304 requests over 64 keys occupying distinct initial buckets. Both modes must produce 98,240 hits and 32,832 source calls. Fixed mode checks 4,096 slots and a 606,448-byte ledger charge at every hot-tail window, while adaptive mode reaches 65,536 slots. Those synthetic IDs qualify the memo mechanism; the real-query fixture must independently qualify its actual store IDs before timing.

The larger working-set control starts with 8,192 references to one key, then cycles eight times over 8,192 keys selected to occupy distinct 8,192-slot buckets. Thus each 4,096-slot bucket has exactly two cyclic competitors. Fixed mode must have 8,192 total hits and 65,536 source calls; adaptive mode must grow and require less than half as many source calls. Key selection calls the package-visible hash only to construct the access pattern. The tests do not copy hashing, replacement, growth or reservation logic. The adaptive half of each paired control runs first, so it is exercised even when the unchanged runtime subsequently fails the fixed-capacity half.

After a skipped growth boundary, another contract checks that the full position mask still distinguishes keys and that a semantic-version change invalidates reuse even after the same ID is restored through the public Value API. A close/replay contract checks idempotent release, no reopening of a closed memo, readability of consumer-retained Values, and a fresh replay owner. Every successful fixture closure asserts query and manager ledger endpoints of zero and reconciles source calls with lazy initialization observations.

Values are deliberately held by test consumers to isolate capacity behavior from collection. This class does not establish weak-reference collectability, real-store source certification, physical decoder counts, or latency. The existing weak-retention, integration and both IR-lifetime suites remain necessary qualification inputs. The coordinator owns all test execution, report capture, formatting and the living ExecPlan.
