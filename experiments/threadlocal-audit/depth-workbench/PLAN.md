## Existing evidence and boundaries

The 100k ThreadLocal experiments already use a real on-disk LmdbStore through SailRepository with native LMDB. Their RDF fixture is synthetic, but the engine is not mocked. They time embedded full value consumption, not HTTP or Workbench rendering. This phase tests whether the holder-depth delta persists through the actual delivery pipeline, not whether a mock generalizes to LMDB.

Existing donor: experiments/overlay/workbench-e2e. WorkbenchBenchmarkServer starts the actual Spring Boot RDF4J server and Workbench with a loopback-only readiness/metrics filter. Actual QueryServlet delegates QueryEvaluator using the remote HTTP repository client; server tuple evaluation is serialized by BinaryQueryResultWriter, decoded by the Workbench Java binary parser, then emitted as Workbench v2 NDJSON. client.mjs streams and JSON-decodes that output in Node. It is a genuine server/Workbench pipeline, but excludes DOM rendering, IndexedDB and browser GC.

The separate browser.mjs drives the real Workbench UI and measures DOM insertion, a double-animation-frame paint proxy, response completion and UI completion. It does not imply every result is rendered at once: the actual UI/row worker uses windowed storage and IndexedDB. Prior launches failed before navigation because Chromium could not create its singleton Unix socket. Do not bypass that restriction. One normal smoke in this environment is permitted; if blocked, explicitly report HTTP/NDJSON only.

## Proposed matched execution

After baseline/candidate HTTP correctness smokes, prespec four fresh-server forks per arm in A B / B A / A B / B A order. Each server opens the same copied fixture and completes readiness before measurement. Repeated query warmup is necessary for steady-state throughput: initially 20 warmups and 10 measurements per fork, same exact query and fully consumed HTTP response. Pilot qualification may fix practical iteration count before comparative timings, not based on favorable results. Preserve first query separately as cold-application-query latency, not cold OS-cache or restart latency. No concurrent-load/QPS claim from sequential requests.

Measure response headers, first received NDJSON row, full 100k window, terminal complete/count and EOF. Primary Workbench latency is full completed response; first-row latency remains separate. Full-query row throughput is 100k divided by full response time, not served-request capacity. Record server/client RSS separately, exact commands/class hashes/flags, GC logs and process origins. All samples retained. Pair by fresh-server block and report fork means, ranges and uncertainty.
