# Lifetime tracking after repository preparation

Source review 2026-11-17. Production baselines remain main be0c4c724f and combined b8104ecf51. No production changes, new test runs, or new performance claims in this review.

## Verified contract

`RepositoryValueIteration.prepareNext` snapshots the current row, checks readiness, captures owners for uncertain roots and resolves complete recursive value waves before setting `rowReady`. `next` returns only after that preparation. Already-prepared roots avoid decode; partialReady also avoids traversing ready roots in mixed rows. This is demand-driven row preparation, not leaving exposed repository values cold until close. The shallow snapshot preserves Value identity while stabilizing reused source containers.

This boundary does not imply all internal Sail values, extension callback values, or raw Sail results are ready. `LmdbRepositoryValueExposureTest.rawSailStatementsRemainLazy` and `functionCallbackStaysLazyUntilRepositoryResult` explicitly distinguish these routes.

## Which ownership protects what

* **Exact current repository pull:** ReplayableIteration.next in LmdbStoreConnection checks its weak repositoryExposure owner and `isPullingSource()`. Only that exact owner skips `rawExtractor.extract(...protectValueTree)`. The repository result scope was admitted before even source.hasNext, retaining the row's ID epoch through preparation even if source.next closes its own scope. Thus the obvious duplicate external-ownership promotion is already removed. Test `exactRepositorySourceReleasesWithoutLegacyColdOwnership` verifies ready retained values are not externally owned and no pinned snapshot remains after result exhaustion and clear.
* **Nested callbacks/raw result escape:** `protectValueTree` transfers cold ownership using each native shell's exact revision capability without decoding lexical data. A callback can retain a value that never appears in the final projected row. A nested raw source is not the exact SOURCE_PULL owner, so it must not inherit the suppression. Tests cover nested raw ownership, foreign nested outputs, earlier snapshot values and cross-store captures.
* **Current-row preparation:** RepositoryValueIteration keeps per-store result scopes and captures Lazy owners before resolving. It borrows an open transactionScope only if it protects the required revision; otherwise it uses a result scope. This cannot be replaced by assuming the transaction remains open.
* **Transaction completion:** `multipleResultsBorrowTheTransactionReaderAndBufferedRowsSurviveItsCompletion` prepares two rows, rotates/closes the transaction, then returns both ready rows without admitting another reader. `sourceClosingDuringNextCannotReleaseTheRowsOlderEpoch` protects a different earlier interval. These are different cases and both matter.
* **Reader retirement/replay:** ValueResolutionScope separates epoch reservation from per-thread native readers. retireReaders increments generation and drains obsolete leases while preserving logical ID identity. close also releases epoch reservation. Removing the scope risks ID reuse or obsolete native-reader access even though the eventual repository output is ready.
* **Observed operation bookkeeping:** executeObservedRead still counts active reads, activates value scope, external callback initializer, read-resource context and worker admission, validates native snapshots, checks cancellation, and unwinds contexts/deferred closes. It is already a lighter observed-result path, not full private replay bookkeeping. Worker capture preserves admission generation, read views, preferred view, scope and cancellation generation.
* **Concurrent close:** RepositoryValueIteration beginCall/endCall and deferred drain avoid releasing native protection while an admitted callback/pull is active. Close cancels the source without waiting for application code. The eventual ready output contract does not eliminate this in-flight race.

## Profile interpretation

Combined no-writer nearest-frame lifetime category is 27.05% of sampled main-thread CPU, not 27% deferred decoding or removable work. Readiness literal-child lambda alone is 4.46% leaf samples. Allocation attribution includes executeObservedRead 2.18 GB, enterReadResourceContext 1.04 GB and activateExternalValueInitializer 1.00 GB. These are candidate mechanism costs, not measured savings. No flame-graph category proves which safety obligation is redundant.

## Concrete simplification candidates, ranked

1. **Specialize foreground activation without changing ownership.** ValueResolutionScope.activate(false) currently reads current Thread, readers.get(thread), and generation and captures them, although those values are only used in the releaseTaskReader branch. A dedicated foreground implementation needs only ACTIVE previous/set/restore. JIT may already eliminate some work, so inspect/profile an isolated change rather than claim a win. Preserve restoring a previously closed exposure and nested distinct scopes. This is the narrowest source-supported redundant bookkeeping candidate.
2. **Readiness work per unique exact value within one row.** Repeated projected values and repeated datatype children can repeat isPrepared traversal; memo produces shared Values. Consider a small identity-based or layout-aware per-row readiness cache, not a global 'ready once' assumption. A cache itself can cost more than checks; only enable where repeated identities justify it. Test mutable/foreign literal and TripleTerm shapes, Lazy initialized parent with cold child, cross-store values, changing revisions, duplicate aliases and uncertain children. Keep full fallback. Compare allocations as well as CPU.
3. **Guarded fused source hasNext/next exposure.** Repository prepareNext calls source.hasNext and source.next separately, potentially installing/unwinding observed contexts twice. Explore a private exact-owner pull method that preserves availability/end semantics and runs both within one tracked read, without pulling a later row. This requires a new internal contract and is higher risk: callbacks in hasNext may close the connection, mutate transaction state, cancel, dispatch workers or throw. Preserve checks between availability and next, replay observation boundaries, wrapper behavior and nested callbacks. Do not implement by keeping thread locals active between public API calls.
4. **Immutable owner-specific context descriptors, scoped activations.** Some captured lambdas/suppliers can perhaps live on ReplayableIteration instead of being recreated every pull. Only cache descriptors whose owner/view relationship is stable; captured admission generation, cancellation generation and preferred native view are not automatically stable. Keep per-call restoration tokens where nesting changes previous context. First measure allocation at exact activation call sites.

Not justified: disabling protectValueTree globally, removing external initializers just because a query is compiled, treating parallel=false as proof no callback can dispatch work, dropping epoch reservations, or extending live context beyond a synchronous pull.

## Validation gates for any implementation

Reuse RepositoryValueIterationTest (source closes during next, transaction-completed buffered rows, map growth, cancellation/fatal errors, no later-row pull); LmdbRepositoryValueExposureTest (reused rows, nested raw callbacks, exact-source no-promotion, cross-store/earlier-snapshot values); LmdbExternalValueBoundaryTest (functions, listeners, configured factories with and without explicit transaction). Add direct activation nesting/restore tests, close/retire while active, worker capture across cancellation generation, and replay with conflicting caller context as applicable. Run relevant full replay/ownership suites before matched profiles. Existing test source is evidence of intended contracts; this review has not rerun those tests.

Recommended first experiment: foreground activation specialization, independently measured. In parallel, compact stable BindingSet snapshots remain the larger allocation opportunity identified by the profile; they should not be conflated with eliminating ownership protection.
